13. Configuration

13.1 One file, one source

Hune reads its configuration from one HCL file. Each subcommand that needs a configuration takes the option --config <path> (short form -c <path>). There is no default path: a subcommand without the option stops with the exit code 2. These subcommands are the exceptions:

  • version and print-reference read no configuration (13.21).
  • copy-store takes --from <path> and --to <path> in place of --config (section 5).
  • import-grafana without --write takes --config as an option (section 15).

The file is the only source of the configuration. Hune reads an environment variable only when an attribute of the file names it with _env (13.5). Hune reads a file other than the configuration file only when a key names it.

Hune reads the file one time, at start, into one typed structure. The rest of the code reads only this structure. A change of the file has an effect only after a restart (13.26).

The engine is hclconf, a crate of this workspace with a PROVENANCE file. It is written for Hune from this section. It has these three rules:

  1. A duration has exactly one integer and one unit (13.4). The texts 1m 30s, us and ns are not valid.
  2. A block can depend on a mode key, as an attribute can.
  3. A boolean key can be a mode key.

The annotations of a dashboard (4.5b) add no key. Their limits are constants of the code: 8 annotations, 1,000 rows for each query, 2,000 marks for each panel and the limits of a text (4.35). The keys max_result_rows, max_result_bytes, max_execution_time and max_concurrent of a source apply to an annotation query as they apply to a panel query. A closed configuration has nothing new to check. The configuration reference does not change.

13.3 Syntax of the file

The file is a subset of HCL:

  • Blocks, labelled blocks (clickhouse "prod" { }) and attributes (name = value).
  • Values are literals only: a text in double quotes, a whole number, true, false, or a list in brackets.
  • A text has the escapes \", \\, \n, \r, \t and \uXXXX. A text ends on its line.
  • Comments start with # or //, or sit between /* and */.
  • The engine refuses expressions, operators, functions, variables, templates (${...} and %{...}), heredocs, objects and null. The error names the key and says "write a literal value".
  • A text with a character that a literal never needs outside quotes (? : + - * / % ! < > & |) is a syntax error.

A syntax error and a duplicate attribute stop the check at once: the list then has one error. Each other error is in the list, in the order of the file (13.25).

13.5 _env and _file

An attribute <name> that accepts the indirection has three forms:

  • <name> = "...": the value is in the file (form V).
  • <name>_env = "VAR": the value is in the environment variable VAR (form E).
  • <name>_file = "/path": the value is the content of the file at /path, without one last line end (form F). The last line end is \n or \r\n.

These rules apply:

  • Give exactly one form. Two forms stop the start, and Hune then reads neither the variable nor the file.
  • No form of a necessary key stops the start.
  • A secret accepts only E and F. A secret in clear text stops the start, also together with another form. The error never shows the value.
  • A key that does not accept the indirection refuses <name>_env and <name>_file.
  • A variable that is not set, or whose value is empty, stops the start. A value that starts or ends with a space or a line end stops the start. A value that is not UTF-8 stops the start.
  • A file that Hune cannot read stops the start. A file content that is empty or not UTF-8 also stops the start. So does a content of more than 65536 bytes, or with a byte order mark.
  • The name of the variable has A-Z, a-z, 0-9 and _, and does not start with a digit. The names SSL_CERT_FILE and SSL_CERT_DIR stop the start (13.23).
  • The error gives the attribute and the variable or the path, never the value.
  • print-config shows the source of each value: file, env:VAR or file:/path (13.20).

13.6 Paths

  • Each path is absolute: the value of a _file attribute, each key whose name ends in ca_file, and storage.volume.path. A relative path stops the start.
  • A key whose name ends in ca_file is a path key, not an indirection. Hune reads the file as a PEM file (13.13).
  • A path has 1 to 4096 bytes and no NUL byte.
  • _file values and CA files are regular files. Hune opens their last part with O_NOFOLLOW.
  • Section 5 gives the rules of storage.volume.path (absolute, canonical, no symbolic link).

The grammar of tile_url (13.13):

  1. The text starts with https://. Another scheme is refused.
  2. The host is a DNS name in lower case with one dot or more, of 253 bytes at most. A label has 1 to 63 bytes of a-z 0-9 -, with no - at the start or at the end. 13.23 The environment rule

Hune reads no environment variable that the file does not name. These are the rules of the code:

  • The first statement of main calls CapturedEnvironment::capture_and_clear() of hclconf, before any other thread starts. It copies the environment, then removes each variable from the process.
  • The engine reads the variables that _env attributes name from this copy, at start, one time.
  • The process keeps only SSL_CERT_FILE and SSL_CERT_DIR, because hclconf keeps them for a TLS library. No crate of Hune reads them: Hune uses no system CA store (12.14). An _env attribute cannot name them.
  • No crate reads a proxy variable. Hune has no reqwest, and its HTTP clients use no proxy.
  • No crate reads RUST_LOG: the log filter comes from log.level only. No crate reads an OTEL_* variable: Hune has its own OTLP exporter (14.9).
  • The job policy searches the sources for the pattern env::(var|var_os|vars|vars_os|set_var|remove_var)\b. It permits a match only in crates/hclconf/src/env.rs, in the tests and in each build.rs. The tests and build.rs are not code of the binary.
  • The crate mongodb is a local copy with no environment read (8b.2). The original reads the variables of the platforms (for example AWS_REGION, K_SERVICE and VERCEL), KUBERNETES_SERVICE_HOST and the file /.dockerenv to fill the metadata of hello. The job policy searches the copy and crates/ for each read. The list of the reads that this check accepts is empty (16.18).

The audit of the dependency tree of the binary found reads in other crates. Hune does not change these crates. Each read sees an empty environment, because main clears the environment first. The result is short:

  • tokio reads TOKIO_WORKER_THREADS only when the builder has no worker count. Hune sets the count. tokio also reads TOKIO_UNSTABLE_SHARDED_BLOCKING_QUEUE in each runtime builder. The variable selects the queue type of the pool of spawn_blocking calls.
  • rustls reads SSLKEYLOGFILE in the type KeyLogFile only. No crate of the tree builds this type.
  • deadpool-postgres (function get_pg_config), hyper-util (feature client-proxy, off) and whoami (locale and desktop functions) read variables in code that Hune does not call.
  • A build script or a procedural macro reads the variables of cargo and rustc at build time. It does not run in the binary.
  • The standard library reads RUST_BACKTRACE and RUST_MIN_STACK. The system resolver reads the files /etc/hosts and /etc/resolv.conf when a host is a name. These files are not variables.

These variables thus have no effect: RUST_LOG, RUST_BACKTRACE, each OTEL_* variable, HTTP_PROXY, HTTPS_PROXY, ALL_PROXY, NO_PROXY (in each case), SSL_CERT_FILE, SSL_CERT_DIR, each PG* variable of libpq, TZ, and each HUNE_* variable. A file can still name any of them with _env, except SSL_CERT_FILE and SSL_CERT_DIR. Example: otlp_endpoint_env = "OTEL_EXPORTER_OTLP_ENDPOINT".

13.26 A change of the configuration

Hune has no reload: no signal and no route reads the file again. To change a value, do these steps:

  1. Edit the file.
  2. Run hune check-config --config <path> with the binary of the instance. Correct each error.
  3. Restart the instance. In the distributed case, restart one instance at a time and wait for /readyz.

A new version of Hune can add, remove or rename keys. The closed schema then stops the start of an old file. The CHANGELOG.md of each release lists each change of a key. Before an upgrade, run check-config of the new binary on the current file (14.18).

14. Observability and operation

14.1 Principles

  • Two listeners: server.listen serves the pages and the API. server.ops_listen serves the probes and the metrics.
  • Logs are JSON lines on the standard output, each with the field event.
  • Metrics use the Prometheus text format and the prefix hune_. They are only on server.ops_listen.
  • Traces go to an OTLP collector when the block telemetry enables them (14.9). Hune has its own small exporter.
  • The durable audit is the history of the store. Hune writes it before the effect (14.11).
  • Each queue and each pool is bounded. Each refusal is an explicit answer (14.14).

14.3 The probe /livez

  • GET /livez answers 200 with the body {"status":"live"} and Content-Type: application/json (6.26).
  • It answers from the bind of server.ops_listen to the exit of the process.
  • It checks no dependency. A failure means a process that does not serve. A restart can help.

14.4 The probe /readyz

GET /readyz follows these rules:

  1. It answers 503 before the first complete load of the catalog.
  2. It answers 200 after the first complete load, while the process does not stop.
  3. It answers 503 from the signal of a stop (14.13).
  4. After the first load, a down PostgreSQL, volume, ClickHouse source or PDP never makes it answer 503.

Rule 4 prevents a full outage. A readiness that fails on each instance at the same time removes all of them. But the catalog in memory can still serve the dashboards.

  • It sends GET /livez to server.ops_listen. A wildcard host becomes the loopback address of the same family (127.0.0.1 or ::1).
  • One deadline of 2 s covers the connection and the answer.

14.6 The log format

  • serve writes one JSON object for each line, in UTF-8, on the standard output. The other subcommands follow 13.19 to 13.21 and section 4, 5 and 15.
  • Each line has ts, level and event first. ts is the time in UTC, in RFC 3339 form with milliseconds and Z, for example 2026-11-09T10:15:30.123Z. level is error, warn, info or debug.
  • A line that belongs to a request also has request_id. When telemetry is on, it also has trace_id and span_id.
  • The other fields of each event are in 14.7. A field without a value is null.
  • log.level sets the lowest level that Hune writes. The order is debug, info, warn, error.
  • A line has 16 KiB at most. Hune cuts a longer text field, adds ... to it, and adds the field truncated with the value true.
  • The writes to the standard output block the writer. The container runtime reads the output.

The request id:

  • When the request has X-Request-Id with 1 to 128 characters of A-Z a-z 0-9 . _ : -, Hune keeps it.
  • Else Hune makes one: 32 lower-case hexadecimal characters from the random source of the system.
  • Hune sends it in the answer header X-Request-Id, to ClickHouse in log_comment (section 8), and to the PDP in X-Request-ID (11.12).

14.9 The telemetry block and the OTLP exporter

The block telemetry has the keys of 13.9. With enabled = false, Hune makes no span and runs no exporter. With enabled = true, the exporter follows these rules:

  • Protocol: OTLP/HTTP with the JSON encoding. Each export is a POST to <otlp_endpoint>/v1/traces with Content-Type: application/json and User-Agent: hune/<version>.
  • Client: the own hyper client with rustls (12.14). It uses no proxy and reads no environment variable. No OpenTelemetry SDK is in the build.
  • Resource attributes: service.name = telemetry.service_name, service.version = the version of Hune, and service.instance.id = a random UUID made at start. The scope name is hune.
  • Queue: 2048 spans. When the queue is full, Hune drops the new span and adds 1 to hune_telemetry_dropped_spans_total.
  • Export: each export_interval, or at once when 512 spans wait. One export at a time. One export has 512 spans at most.
  • Deadline of one export: the lower of 10 s and export_interval.
  • Failure: no connection, the deadline, or a status other than 2xx. Hune drops the spans of that export and adds their number to the counter. It never sends them again. The line telemetry.export_failed comes one time for each change of state.
  • At a stop, Hune exports the queue one last time, for 2 s at most (14.13).
  • An export never delays a request. The telemetry is best effort and is never the audit.

An example of the block:

hcl
telemetry {
  enabled         = true
  otlp_endpoint   = "http://otel-collector:4318"
  service_name    = "hune"
  export_interval = "15s"
}

14.11 The audit trail

  • The durable audit is the history of each dashboard in the store (section 5). Hune writes the history record before the effect is visible. On the volume, it writes it before the rename. On PostgreSQL, it writes it in the same transaction.
  • A change whose history record cannot be written does not happen. The client gets the error of section 5.
  • The record holds the version, the kind of change, the time and the subject (sub, or - in the mode open). It also holds the message, the save_id, the folder, the etag and the document (section 5).
  • After the effect, Hune writes the log line dashboard.changed (14.7). The log line is not the audit: a lost log line loses no record.
  • A change of a folder writes the log line folder.changed.
  • OTLP is never the audit.

14.12 The start sequence

hune serve --config <path> does these steps in this order:

  1. Capture and clear the environment (13.23).
  2. Read and check the configuration (section 13), with the PEP configuration and the action document (13.13). An error: the errors on the standard error, exit 1.
  3. Write server.config, server.config.sources and each config.warning (13.22).
  4. Build the TLS configurations, the clients of the sources and the PEP. With server.compress_static = true, make the gzip copies of the static files (9.3). This step sends nothing on the network.
  5. Bind server.ops_listen. A bind error: server.start_failed, exit 1. The ops listener serves at once: /livez answers 200, and /readyz answers 503.
  6. Open the store (section 5). For the volume, do its checks and take its lock. For PostgreSQL, do the checks of 5.29: the connection, the encoding, the schema version and the role (12.13). Each check that fails writes server.start_failed with the message of 5.29, and exits with 1.
  7. A failed connection to PostgreSQL gets a retry only for four causes. They are a network failure, a timeout, the SQLSTATE 57P03, and a server that is a standby. Hune then retries each storage.postgres.connect_timeout, with no limit. Each such failure writes store.sync_failed one time for each change of state. /readyz stays 503.
  8. Load the catalog: store.loaded.
  9. Start the tasks: the poll or the scan of the store, the pings of the sources and the OTLP exporter.
  10. Bind server.listen and accept on it. A bind error: server.start_failed, exit 1. /readyz answers 200. Write server.listening and server.ready.

Three connection failures stop the start at step 7 with server.start_failed and the exit code 1. They are an SQLSTATE of the class 28 (the authentication failed) and the SQLSTATE 3D000 (the database does not exist). The third is a failed check of the certificate or of its name. They are errors of the configuration or of the account, and a retry cannot repair them.

14.13 The graceful stop

SIGTERM and SIGINT start the stop. The binary is the process 1 of the container, and it handles both signals itself. G is server.shutdown_grace. SHUTDOWN_DRAIN is a constant of 5 s.

  1. Write server.stopping. /readyz answers 503. hune_stopping is 1.
  2. Wait for SHUTDOWN_DRAIN. During this time, Hune serves each request as usual. The container platform and the proxy remove the instance from their lists, which they do some time after the signal.
  3. Stop the accept on server.listen. Close the idle connections. A request that comes on an open connection gets 503 server_stopping with Connection: close.
  4. Let the requests in flight continue, for G minus 3 s at most.
  5. Close the connections of the queries still in flight. ClickHouse cancels them (section 8). A PostgreSQL source gets a cancel request first (8a.7). Their requests get 503 server_stopping. A write to the store continues: a PostgreSQL transaction commits or rolls back, and a write to the volume ends. This step waits 1 s at most.
  6. Stop the tasks of step 9 of 14.12. Close the pools. Export the OTLP queue, for 2 s at most.
  7. Close server.ops_listen. Write server.stopped and exit with 0.

When requests are still in flight at the end of step 5, Hune writes server.shutdown_timeout, does step 6 and exits with 1. A second signal during the stop writes server.signal_again and exits with 1 at once.

A call of the PEP that blocks cannot stop early (11.13). The exit does not wait for it.

The budget of a stop is G plus SHUTDOWN_DRAIN. Give the container more time than this budget. Set stop_grace_period in compose and terminationGracePeriodSeconds in Kubernetes to G plus SHUTDOWN_DRAIN plus 5 s at least. For G = 30 s, use 40 s (section 17).

14.14 Limits and back-pressure

These rules apply to each resource:

  • Each queue, pool and cache has a bound. 12.16 gives the bounds and the answers.
  • When a bound is reached, Hune answers at once with an explicit code. It never keeps a request in an unbounded queue.
  • A refusal that can succeed later has retryable: true. The header Retry-After gives the wait in seconds: 1 for server_busy and source_busy, 5 for storage_unavailable.
  • A wait for a place is bounded by a key: queue_wait for a source, access.pdp.timeout for the PDP pool and storage.postgres.statement_timeout for the PostgreSQL pool.
  • Hune never repeats a write by itself. The browser repeats a save with the same Idempotency-Key (section 10).
  • The browser runs at most 6 panel queries at one time for each tab (section 9).

14.19 Runbook: upgrade with migrate-store

serve stops at start when the schema version of the database differs from the version of the binary (section 5). Thus a change of the schema stops each instance for some minutes.

  1. Run hune check-config of the new binary on config.hcl and on migrate.hcl.
  2. Make a backup with hune export of the old binary. Also make a CloudNativePG backup.
  3. Scale the Deployment to 0. Wait until no pod runs.
  4. Run hune migrate-store --config /etc/hune/migrate.hcl of the new binary as a Job. Wait for the exit code 0.
  5. Apply the grants that the CHANGELOG.md of the release names (5.25).
  6. Scale the Deployment back with the new binary.
  7. Find server.ready in each pod.

From step 3 to step 6, the dashboards are not available. The old binary refuses the new schema. For a rollback, restore the backup of step 2 into a new database (14.22). Then start the old binary on it. The saves made after step 6 are lost in this case.

14.20 Runbook: upgrade with migrate-documents

The server reads only the current format_version (section 4). A change of the format thus needs a stop.

  1. Run hune check-config of the new binary on the current file.
  2. Make a backup with hune export of the old binary.
  3. Stop each instance.
  4. Run hune migrate-documents of the new binary as section 4 gives. Run the dry run first and read its report. A warning names a document that the command does not migrate (4.42, item 8).
  5. Run the command again in the mode that writes.
  6. In the LOCAL case with git, commit the changed files in one commit.
  7. Start the new binary.
  8. Check that the log has no store.document_invalid line.

For a rollback, restore the backup of step 2 (14.22) and start the old binary.

14.21 Runbook: rotation of a key or a secret

Hune reads each secret, each key and each CA file one time, at start (12.10). Each rotation thus needs a restart.

The public key of the edge (mode authzen):

  1. Make sure that each token of the edge has a kid equal to the configured kid of its key. The log of the last max_age must hold no line access.unauthenticated with reason = "kid". Without this step, the second key of step 1 makes Hune refuse each token without kid (11.8).
  2. Add the new key to the text of access.identity.public_keys: a new PEM block, or a new JWK with its kid.
  3. Keep the old key. Restart each instance.
  4. Make the edge sign with the new key.
  5. Wait for max_age plus clock_skew. Then each token of the old key has expired.
  6. Remove the old key from the text. Restart each instance.

The PDP token:

  1. Make the PDP accept the old token and the new token.
  2. Write the new token to the file of access.pdp.token_file. Restart each instance.
  3. Make the PDP refuse the old token.

A ClickHouse password:

  1. Write the new password to the file of password_file of the block.
  2. Change the password of the user in ClickHouse.
  3. Restart each instance at once.

Between step 2 and step 3, the queries of an instance fail with the authentication error of section 8.

The PostgreSQL password:

  1. Write the new password to the file of storage.postgres.password_file.
  2. Change the password of the role in PostgreSQL. With CloudNativePG, change the Secret of the role.
  3. Restart each instance, one at a time.

Between step 2 and step 3, the saves fail and the reads continue from the catalog.

A CA certificate of ClickHouse, PostgreSQL, the PDP or the collector:

  1. Add the new CA certificate to the CA file, next to the old one. Restart each instance.
  2. Change the certificate of the server.
  3. Remove the old CA certificate from the file. Restart each instance.

14.22 Runbook: restore

Section 5 gives the subcommands export, import and restore and their options. The restore drill of section 16 tests the procedure A.

Procedure A, a whole store from an export:

  1. Stop each instance.
  2. Make an empty store: an empty directory for the volume, or a new database with hune migrate-store.
  3. Run hune import --config <path> with the directory of the export.
  4. Start the instances.
  5. Compare the counts of folders and dashboards of store.loaded with the export.

Procedure B, one deleted dashboard, with hune restore and its uid (section 5):

  • Volume: stop serve, because hune restore takes the lock of the volume. Run hune restore, then start serve.
  • PostgreSQL: run hune restore while serve runs. The next poll shows the dashboard.

Procedure C, an old version of a dashboard: use the history of the page, or POST /api/dashboards/{uid}/restore. This makes a new version and needs no stop.

Procedure D, PostgreSQL to a point in time:

  1. Recover the CloudNativePG cluster into a new cluster.
  2. Change storage.postgres.host, storage.postgres.tls.server_name and storage.postgres.tls.ca_file to the service and the CA of the new cluster.
  3. Run hune check-config on the changed file.
  4. Restart each instance.

Procedure E, the volume from git: run git checkout of the commit in the volume. The scan finds the changes and records each one as an external change (section 5).

14.23 Runbook: PostgreSQL failover

With CloudNativePG, a lost primary gives 1 to 2 minutes with no primary. Hune does this during the failover:

  • The catalog serves the lists, the dashboards and the panel SQL. The panel queries run.
  • A save gets 503 storage_unavailable with Retry-After: 5. The page keeps the draft (section 10).
  • hune_store_up is 0, hune_store_catalog_age_seconds grows, and the log has store.sync_failed.
  • /readyz stays 200.
  • Each connection has target_session_attrs=read-write. A former primary that returns as a replica gets no write.
  • After the promotion, the next poll succeeds. The log has store.sync_recovered.
  • A save that the browser repeats with the same Idempotency-Key makes one version only.

The operator does these steps:

  1. Do nothing in Hune during the failover. Watch hune_store_up.
  2. When hune_store_up stays 0 for more than 5 minutes, check the state of the PostgreSQL cluster.
  3. When the cluster has a primary and hune_store_up stays 0, check the network policy and the Secret of the role.
  4. Restart one instance and read its log. A wrong password, an absent database or a failed certificate check stops it with server.start_failed (14.12). A network failure gives store.sync_failed while it retries.

14.24 Runbook: a stuck volume lock

The symptom: serve stops at start, and its error says that another process holds the lock <root>/.hune/lock (section 5).

The kernel releases a flock when the process that holds it ends. A held lock thus means one of two things. A process holds it now, or an NFS server keeps the lock of a client that crashed.

  1. On the host of the volume, find the process that holds the lock: fuser -v <root>/.hune/lock.
  2. When it is another Hune or a hune import, stop it. Two writers on one volume are not supported.
  3. When no process holds it and the volume is NFS, wait for the lease time of the NFS server. The default lease of NFSv4 is 90 s. Then start Hune again.
  4. Do not delete the lock file to start a second writer. A delete does not release the lock of a process that runs, and two writers then race.
  5. When a volume must have more readers, start them with storage.volume.read_only = true. They take no lock.
