11. Access and ProcurAuth

11.1 Principle

ProcurAuth is OPTIONAL. The operator selects it at run time with the key access.mode. One binary serves both modes. No Cargo feature removes ProcurAuth, so the test matrix stays one build.

In the mode authzen, access has three parts:

  1. Authentication. The edge authenticates the person and signs an identity token. The edge puts the token in a request header.
  2. Check of the token. Hune checks the token on each request. The token gives the subject.
  3. Decision. Hune asks a PDP for each operation with the AuthZEN Authorization API 1.0. Hune is the PEP.

In the mode open, Hune does none of these parts. A reverse proxy that authenticates the users decides who reaches Hune (12.5, 12.6).

Hune applies each decision on the server. The page in the browser shows or hides controls (11.25). The page never decides.

11.2 The access block and the two modes

The block access is necessary. The key access.mode is necessary and has no default value. A file without the block or without the key stops the start. Thus nobody gets the mode open by mistake.

access.modeBehaviour
openHune reads no token, asks no PDP and trusts no identity header. Each request has the subject -. The blocks identity and pdp stop the start. The two ProcurAuth routes answer 404.
authzenHune checks the identity token of each request and asks the PDP for each operation. The blocks identity and pdp are necessary.

The words open and authzen are the words of ClickHouse Dash. An operator of this product knows them.

11.6 Start checks of the access block

These items stop the start, before Hune serves. 13.14 gives the exact error text of each item.

  • No block access, no key access.mode, or a value other than open or authzen (lower case).
  • mode = "open" with a block identity or a block pdp.
  • mode = "authzen" without the block identity or the block pdp, or without one key of these blocks.
  • An http URL in pdp.url with plain_http = false, or an https URL with plain_http = true.
  • pdp.ca_file with plain_http = true, or no pdp.ca_file with plain_http = false.
  • A pdp.url with a user name, a password, a query or a fragment.
  • The PDP token in clear text. Give token_env or token_file.
  • Two forms of one key, for example public_keys and public_keys_file.
  • A text in public_keys that breaks a rule of 11.9.
  • A forbidden name in identity.header (11.8).
  • An identity.audience that is not an id of P 4.1: 1 to 256 bytes of UTF-8 with no control character.
  • A max_age or a clock_skew that is not a whole number of seconds.
  • A key max_concurrent_per_subject in a clickhouse block with mode = "open", or no such key with mode = "authzen".
  • An error of the PepConfig or of the action document. Stage 2 of the checks builds both without network (13.13), so check-config also finds this error. The error names the key (13.14).

Hune does not contact the PDP at start. The PEP reads the PDP metadata at the first question (11.12). Thus a PDP outage never stops the start and never causes a loop of restarts.

11.8 The identity token

procurauth-pep checks the token with Pep::authenticate (P 9.4). Hune adds one rule (the subject rule below) and removes no rule.

  • The token is in the header that access.identity.header names. Hune never reads the token from Authorization, from a cookie or from a query parameter.
  • Two copies of the token header are a refusal.
  • The header name follows the token rule of RFC 9110. The names Authorization, Proxy-Authorization, Cookie, Host, Content-Type and Content-Length stop the start, in any case.
  • The token has 16384 bytes at most.
  • The JOSE header member alg is exactly Ed25519 or ES256. Hune refuses EdDSA, none, HS256 and each other name.
  • The JOSE header member typ is exactly JWT. A token without typ, or with another value such as at+jwt, is refused.
  • A JOSE header with the member crit is refused. A duplicate member in the header or in the claims is refused.
  • When the key set holds two or more keys, the token must have a kid that the set holds. When the set holds one key, a token without kid uses that key.
  • The claims iss, sub, aud, iat and exp are necessary. iss equals access.identity.issuer. aud equals access.identity.audience, or is an array that holds it.
  • iat and exp are whole numbers of seconds. A fraction, an exponent or a sign is refused.
  • Hune refuses a token when its clock is later than exp plus clock_skew. It refuses a token whose iat is later than its clock plus clock_skew. It refuses a token whose exp minus iat is more than max_age.
  • The subject rule of Hune: sub has 1 to 256 bytes of UTF-8 with no control character. It is not one of the reserved texts of the history: -, external and import-grafana (section 5). Another sub is refused.
  • Hune treats sub as opaque text. It sends sub to the PDP as the subject id with the type user. It sends no other claim (P 3.3, P 9.6).
  • Hune ignores each unknown claim. It writes owner in the access log only. It never uses owner in a decision (P 9.5).

Two of these rules come from procurauth-core, and Hune follows the library for both. iat and exp must be whole numbers: the library refuses a fraction, a sign and an exponent. A token must have a kid when the key set holds two or more keys. ClickHouse Dash accepts a fraction, a sign and an exponent in iat and exp, and rounds the value down. Issue 1 of the repository ProcurAuth/procurauth asks this question of the protocol, and section 19 holds it as an open item. Its title is "Section 9.4: can iat and exp have a fraction, a sign or an exponent?".

Hune keeps no result of a token check. It checks the token again on each request. P 9.7 permits a cache, but a check costs less than 0.1 ms.

A request with no valid token gets 401 unauthenticated. The body gives no reason. When the request has a body, the answer also has Connection: close, so Hune does not read the body. The log line access.unauthenticated (14.7) gives the reason: missing, duplicate_header, structure, header, alg, typ, kid, signature, claims, iss, sub, aud, iat, exp, life or subject.

11.9 The public keys

access.identity.public_keys holds PEM text or a JWK Set (RFC 7517). These are the rules of ClickHouse Dash. Hune parses the text itself with these rules. It never gives the text to KeySet::from_jwks_value of procurauth-core, which refuses some keys that these rules accept. For each key, Hune writes an SPKI PEM block and calls PublicKey::from_spki_pem(pem, Some(kid)). It gives the list of the keys to KeySet::from_keys.

Hune reads the text as a JWK Set when its first character after spaces, tabs and line ends is {. Else it reads PEM.

  • PEM: 1 to 16 blocks -----BEGIN PUBLIC KEY-----. Each key is Ed25519 (for Ed25519) or P-256 with an uncompressed point (for ES256). Outside a block, a line must be empty. Other text, a PEM header, a private key and another type of key stop the start. The base64 text of one block has 4096 bytes at most.
  • JWK Set: a JSON object with a member keys, an array of 1 to 16 keys. A key of type OKP has crv Ed25519 and x (RFC 8037). A key of type EC has crv P-256, x and y (RFC 7518). The point of a P-256 key must be on the curve.
  • The member alg of a JWK is optional. When it is present, it is Ed25519 or EdDSA for OKP, and ES256 for EC. A token whose header has alg EdDSA stays refused (11.8).
  • The members use and key_ops, and each other member that this list does not name, have no effect.
  • A JWK with a private member stops the start: d, p, q, dp, dq, qi, oth or k. A JWK with another kty or crv stops the start. A duplicate member, or data after the JSON object, stops the start.
  • The kid of a JWK is its member kid: 1 to 256 bytes with no control character. A PEM key, or a JWK without kid, gets the RFC 7638 thumbprint of the key as its kid. Two keys with the same kid stop the start.

Use a JWK Set with an explicit kid for each key. Make the edge put this kid in each token. With two or more keys, Hune refuses a token without kid or with another kid (11.8). A PEM key has the RFC 7638 thumbprint as its kid, so the edge must then send that thumbprint.

hune print-config shows each key as its type and its kid, for example ["Ed25519 kid=kPrK_qmxVWaYVA9wwBF6Iuo3vVzz7TxHCTwXBygrS4k"] (13.20). Hune reads the keys one time, at start. A change of the keys needs a restart (14.21).

11.12 The PDP transport

The library is synchronous. It uses std::net::TcpStream and has no TLS code. Hune gives its own type that implements the trait procurauth_pep::transport::PdpTransport. These are its rules:

  • TCP: TcpStream::connect_timeout with TCP_NODELAY. One deadline of access.pdp.timeout covers the TCP connection and the TLS handshake.
  • TLS: the crate rustls with the provider ring, TLS 1.2 and TLS 1.3 only. The trust roots are only the certificates of access.pdp.ca_file. The server name is the host of access.pdp.url. Hune sends no client certificate.
  • HTTP/1.1 only. A POST has a Content-Length. Hune sends the headers that the library gives (Authorization, Content-Type, Accept). It adds Host, X-Request-ID (14.6) and, when telemetry is on, traceparent (14.10).
  • The library gives the transport no context of the request. Before each call of the library, the task puts the request id and the trace context in a thread-local value of its thread. The transport reads this value for X-Request-ID and traceparent. The task clears the value after the call.
  • The answer can use Content-Length or chunked encoding. An answer of more than 262144 bytes is the failure TooLarge.
  • No redirect: a status 3xx is an answer with that status. No proxy. The transport reads no environment variable.
  • supports_scheme("https") is true. supports_scheme("http") is true only when access.pdp.plain_http = true.
  • The transport keeps idle connections, at most access.pdp.max_connections. It closes an idle connection after 5 s, or earlier when the PDP publishes procurauth_idle_max_seconds: after half of that time (P 10.7).
  • The deadline of one exchange is the timeout that the library gives. It starts at the first byte written.

The transport gives the kind of each failure to the library. The library uses it for P 10.6.

11.13 The bounded blocking pool

The calls of the library block the thread. Hune runs them out of the async workers:

  • Each call that can send a request to the PDP runs in tokio::task::spawn_blocking. These calls are Pep::decide, Pep::check, Pep::display and the options walk of 11.26.
  • Before the call, the task takes one permit of a semaphore with access.pdp.max_connections permits.
  • The task waits for a permit for access.pdp.timeout at most. When no permit comes in this time, the operation gets 503 pdp_unavailable. The log line access.pdp_failed has error = "pool_busy".
  • Pep::authenticate sends no request. It runs on the async worker.
  • A call of the library cannot stop early. Each call runs in its own task. When the client closes the connection, the call continues to its end, and it gives back its permit. Its answer goes to the cache, except the answer of a question that is never kept (11.27).
  • The metric hune_pdp_pool_in_use gives the number of permits in use (14.8).

The longest wait of one PDP request is thus three times access.pdp.timeout: the permit, the connection and the exchange. An operation with other permissions sends at most two PDP requests in sequence (11.21). A restore sends at most three: the use alone before the store read, then the others, then the use (11.21).

One call of the library can send more than one PDP request under one permit. A batch above the maxima of the PDP becomes several requests (P 10.7a). The first question of each PEP of 11.27 also reads the metadata. Each request has its own deadline. A list uses the two calls of 11.25. With the default maximum of 50 items in each request, these are the bounds:

  • One call of Pep::display with n questions sends at most n / 50 requests, rounded up, and one read of the metadata, under one permit.
  • One call of Pep::check sends one request under its own permit. Several such calls run at the same time, within the permits of the pool.
  • One page of GET /api/dashboards asks at most 200 questions (11.25), so it sends at most 200 requests.
  • One request to GET /api/folders asks at most 2001 questions (11.25). It makes one call of Pep::display with at most 1000 questions: 20 requests under one permit. It also makes at most 1001 calls of Pep::check: one request for each, each under its own permit.

11.14 The service id

The service id is access.identity.audience. It has no default value. It is the claim aud of each token and the member server of the action document. It is also the id of the root node of type service. The reference value is dashboards.

11.15 The resource tree

Hune gives each operation a node of this tree:

text
service        access.identity.audience
├── folder     the id of a folder
│   └── dashboard   the uid of a dashboard
└── source     the id of a clickhouse or postgres block

The type folder has the depth 1, the type dashboard has the depth 2, and the type source has the depth 1. P 4.1 permits the depth 4 below the service, so Hune uses 2 of 4.

A folder id and a dashboard uid follow the id rule of section 4: ^[a-z0-9][a-z0-9-]{0,39}$. A source id follows the same rule (13.12, 13.12a). These ids have only characters that P 5.2 does not encode. A grant on a node covers each node below it (P 4.3). A grant on a folder thus covers each dashboard of the folder, now and later.

The chain comes from the in-memory catalog of Hune, never from a value of the request (P 4.5). For a dashboard, the folder comes from the catalog entry of its uid, not from the URL and not from the body.

A move changes the chain of a dashboard. The grants on the old folder no longer apply to it, and the grants on the new folder apply at once.

A change of the folder between the decision and the write is a race. Hune closes it: a write operation gives the store the folder of the chain that the PDP saw. The store refuses the write with 409 conflict when the current folder of the uid is another folder (section 5). The etag does not show a move, because the document does not hold its folder.

11.18 The action document

11.20 Order of the checks

Each request on server.listen passes these steps in this order. A step that refuses stops the request.

  1. Limits: the request line and the URL, the headers, the route, and the declared body size (Content-Length) against the limit of the route (12.16). Refusal: 400, 404, 405, 413, 414 or 431.
  2. Write guard, on each POST, PUT and DELETE (12.7). Refusal: 403 cross_site_request or 415.
  3. Token check, in the mode authzen, on each route except the action document (11.8). Refusal: 401.
  4. Process ceiling: a write route, when no store is the primary store, gets 403 editing_disabled and no question. This includes POST /api/sources/{id}/preview.
  5. Body read, within the limit of the route (12.16). A chunked body above the limit gets 413. A body that does not arrive within 30 s gets 408.
  6. Shape of the request and of its body (section 6). Refusal: 400. The document of a create, a save or a validate_only request stays bytes at this step. Hune checks the JSON syntax of the whole body and reads only the other members.
  7. Catalog lookup. An unknown uid or folder id follows 11.23. An unknown source id gets 404 and no question. For a create and a save, the pre-pass of 11.21 reads the sources of the document before this lookup. Thus an item that exists and an item that does not exist get the same work before the decision (11.23).
  8. Decision: the other permissions in one batch, then the use (11.21). Refusal: 403 or 503. A restore asks the use alone before it reads the version (11.21).
  9. Validation of the document, of the draft of a preview or of the restored version (4.36, 7.18). It runs in spawn_blocking, within the limits of 12.16. Refusal: 422. For a create and a save, the check after the validation follows (11.21). This is the one validation of a restored version: the store does not validate it again (6.18).
  10. Effect: the store write or the query, with the folder check of 11.17 and the ceilings of 11.24.

This is the order of 6.28.

The decision comes before the first call to ClickHouse and before the first write to the store. It also comes before the validation of a document or of a draft. Thus a subject without the right never reaches the validator. The work before the decision is the body read, the syntax check and the pre-pass. Each of these steps is linear in the bytes.

  • An annotation query asks the same question as a panel query: dashboard.read on N(uid). No new action exists, and the action document does not change (11.18).   • A create and a save ask their questions before the validation of the document (11.20). A pre-pass reads the sources from the bytes of the document. It reads the member source of each query variable, of each annotation, and of data.query and each item of data.extra_queries of each panel. A hidden query counts.   • After the validation, each source of the valid document must be in the questions of the decision. Else Hune answers 500 internal_error, writes the log line access.prepass_mismatch (14.7), and writes nothing. Thus a fault of the pre-pass can never skip a question.
  • A document that the pre-pass cannot read (a wrong type, or a list above its budget) asks the use alone. The validation then gives its 422. When such a document passes the validation, the answer is 500, and Hune writes nothing.
  • A restore asks the use alone first, before it reads the version. A false answer gives 403, and Hune reads nothing.   • The questions of each write route of 11.20, the preview included, never use a kept answer, and the library keeps no answer to them (11.27). Each request of a write route thus sends its questions to the PDP.
  • validate_only=true and the preview ask their questions before the validation of the document or of the draft. Thus a 403 comes before a 422.
  • Hune removes each repeated question and each other permission that equals the use.
  • POST /api/sources/{id}/preview runs SQL on the source id only. The body has exactly one of uid and folder, and exactly one of panel and variable (6.22). With panel, the query of the draft panel runs. With variable, the options query of the draft variable runs. With uid, the other permission is on N(uid). With folder, it is on F(f), with f the member folder.
  • Inspect (panel query row): when server.query_inspect is true, Hune asks one more question in one operation. The question is source.query on S(s), with s the source of the query that the request runs (4.15a). A subject can see the SQL of a query of one source and not of another. 11.23 The unknown-uid rule

A uid or a folder id that does not exist must give no information to a subject without the right to see it. Hune applies these rules in the mode authzen:

  1. A route names a dashboard uid that the catalog does not hold. Hune asks dashboard.read on the service, with the match node. A false answer gives 403 forbidden. A true answer gives 404 not_found. A PDP failure gives 503 pdp_unavailable.
    • Hune asks this question at each request. It never uses a kept answer, and the library keeps no answer to it (11.27).
    • On a write route, this question is the use of one operation. Its others are the other permissions of the route that name only items that exist (11.21). Hune asks them first, in one request, as for an item that exists. A false answer for one of them gives 403 forbidden.
    • These others are source.query on each source of the pre-pass for a create and a save. For a move to a folder that does not exist, the other is dashboard.write on N(uid). Hune does not ask an other that names the unknown item. Thus it never asks a question about an item that does not exist.
  2. Rule 1 also applies to a folder id that the catalog does not hold. Such an id can be in PUT and DELETE /api/folders/{id}, in the folder of POST /api/dashboards, in the target of a move, or in a preview.
  3. POST /api/dashboards can name a uid that the store holds in any folder, also as a deleted dashboard (6.13). After a true answer for the use, Hune asks dashboard.read on N(uid) of the dashboard that has this uid. The catalog has no entry for a deleted dashboard: Hune reads its last version with Store::history(uid, None, 1) (section 5) and takes the folder of that version for the chain. A false answer gives 403 forbidden. A true answer gives 409 already_exists.
  4. A panel id, a variable name or a history version that the dashboard does not hold gives 404 not_found. Hune answers this after a true answer for the use of the route, so the subject already has access to the dashboard. A restore asks the use first, before it reads the version (11.21). Thus a version that does not exist gives 404 after the use only, because the others need the sources of the version.
  5. A source id that the configuration does not hold gives 404 not_found and no question. The action document already lists each source.
  6. The 403 of rules 1 to 3 is the 403 of each other refusal of the route. It has the same status, the same headers and the same body. Its member action is the use of the route (11.30). Before the decision, Hune does the same work for an item that exists and for one that does not exist. This work is the body read, the syntax check and, for a create and a save, the pre-pass of 11.21. Hune reads no store and validates no document before the decision.
    • On a write route, the two items also send the same number of PDP requests. They ask the same others, and neither uses a kept answer.

Thus a subject with grants on one folder gets 403 for a dashboard of another folder. It gets the same 403, byte for byte, for a uid that does not exist. A subject with dashboard.read on the service can read each dashboard, so a 404 tells it nothing new.

On a write route, the request count and the use of the cache thus do not show whether an item exists (12.4, T98). The last question of rule 1 is not the use of the route, so the PDP can still take another time to evaluate it. On a read route, the use on N(uid) can be a kept answer, and the question of rule 1 cannot. Two requests for one uid in one cache_ttl can thus take different times (12.18).

In the mode open, each unknown item gives 404 not_found and no question.

11.24 The ceilings and the limits of a source

Each source block has its own limits (13.12, 13.12a). A true answer for dashboard.read or source.query can carry the ceilings max_rows and max_duration in context.limits (P 7.3). Hune applies them to each query that the permission lets run (P 7.4, P 5.5a):

  • Effective max_result_rows = the lower of the key max_result_rows of the source and max_rows.
  • Effective max_execution_time = the lower of the key max_execution_time of the source, in seconds, and max_duration.
  • Without a ceiling in the answer, the key of the source applies alone.
  • Hune sends the effective values to ClickHouse as the settings max_result_rows and max_execution_time, with result_overflow_mode = 'throw' (section 8). The client deadline of section 8 uses the effective max_execution_time.
  • For a PostgreSQL source, Hune enforces the effective values in its own client (8a.6, 8a.7, 11.33).
  • The ceilings change no other limit. max_result_bytes, max_query_size and the concurrency limits stay the values of the source.

11.25 The display filter

The display filter shows each person the items and the controls that the person can use. It is for the display only. The server checks each operation again (11.21). A true answer for the match subtree never lets an operation run (P 4.4).

The library has two calls for these questions. Pep::display asks a batch of questions with the match subtree and gives one answer for each. Pep::check asks one operation without usage, with the match node. Hune calls it with one permission as the use. An outcome that lets the operation run is true, and a refusal 403 is false. A refusal 503 makes the list fail.

The list of dashboards (GET /api/dashboards) uses this procedure:

  1. Hune asks dashboard.read on F(F) for each folder F of the catalog, in one call of Pep::display.
  2. A folder with false is hidden, with each of its dashboards.
  3. For each visible folder, Hune asks dashboard.read and dashboard.write on F(F), each with one call of Pep::check. These calls run at the same time, within the pool of 11.13.
  4. A folder with true for dashboard.read shows with each of its dashboards. A grant on the folder covers each dashboard below it (P 4.3), so Hune asks no more question.
  5. For the dashboards of the other visible folders, Hune asks dashboard.read on N(u) of each dashboard u, in one call of Pep::display. A dashboard has no node below it, so the match subtree gives the display of the match node. A dashboard with true shows.
  6. Each visible folder carries the flag access.write: the dashboard.write answer of step 3. Each visible dashboard carries the access.write of its folder (6.12).

The list of folders (GET /api/folders) uses steps 1 and 2. Then it asks dashboard.write on F(F) of each visible folder with Pep::check, for its flag access.write. It also asks dashboard.write on the service with Pep::check, for the flag access.create at its top level.

The last visible id is the id of the last item that the subject can see, or empty before the first item. The count is the number of children that the walk examined and hid after this item. It is a whole number in decimal digits.

The cursor never holds the id of a child that the subject cannot see. A page with no item keeps the position of its request and adds its children to the count. A cursor of the older form, or with a bad count, gives 400.

A parent that does not exist gives an answer with no item, as P 5.7 says. A PDP that gives no valid answer gives 503 pdp_unavailable, never an empty list. The log line access.options gives the counts (14.7).

11.27 The answer cache

The library keeps the answers of the PDP for access.pdp.cache_ttl at most (P 10.1). These are its rules in Hune:

  • The key of a kept answer is the subject, the action, the resource with its chain, and the match.
  • A kept true answer lets the same operation run with no question. A kept false answer refuses it with no question.
  • A failure is never kept.
  • The cache holds 16384 entries at most. When it is full, the library keeps no new answer (P 10.1b).
  • cache_ttl = "0s" keeps no answer.
  • Each instance has its own cache. A revoked grant can stay active for cache_ttl at most on each instance.
  • A cache hit writes no access.decision line. The metric hune_pdp_cache_hits_total counts it.

The cache does not keep these questions:

  • The questions of each write route of 11.20, the preview included.
  • The question of 11.23 on the service, on each route.

Hune asks them with a second PEP of the library that has no cache. Both PEPs use the same link and the same pool (11.12, 11.13). The second PEP reads the metadata of the PDP at its first question. With cache_ttl = "0s", Hune has one PEP only. Thus a write route sees a revoked grant at once. On a write route, an item that exists and one that does not exist also cost the same PDP requests (11.23).

Hune adds one rule above the library: one flight for each question. The rule applies when cache_ttl is more than 0s. Two equal questions that wait at the same time share one call of the library. Two questions are equal when they have the same key in the cache. The second question waits for the answer of the first. The rule does not apply to a question that the cache does not keep: each request asks its own.

This rule keeps a page with 45 panels at one PDP question for its first refresh. With cache_ttl = "0s", each operation asks its own question (P 10.1).

The load on the PDP is small. One subject on one dashboard with a refresh of 30 s and cache_ttl = "30s" sends about one question each 30 s. Each write request and each request for an unknown item sends its questions to the PDP: three PDP requests at most, in sequence. The pool of 11.13 bounds them.

11.33 The PostgreSQL source in the access layer

A postgres block is a node source:<id> of the tree of 11.15, as a clickhouse block is. The access layer does not tell the two kinds apart. These rules apply:

  • The questions of 11.21 are the same. source.query on S(s) covers a save, a draft run and a preview on a PostgreSQL source. dashboard.read covers a panel query and an options query.
  • The PDP never gets the kind of a source. A rule of the PDP names the source id. The page gets the kind from GET /api/sources (6.22).
  • The action document (11.18) holds one resource for each source block of both kinds. The description of the type source does not name a kind.
  • The ceilings max_rows and max_duration apply as 11.24 says. Hune enforces them in its own client, with the checks of 8a.6 and 8a.7.
  • A row check or a byte check that a ceiling lowered gives 403 ceiling_exceeded, as 8a.8 says. A ceiling of 0 gives 403 ceiling_exceeded before Hune sends the query.
  • When the ceiling equals the key of the source, the ceiling is the cause (11.24).
  • A grant of source.query gives each read that the role of the source permits (8a.13). It gives no write: the role cannot write, the session cannot, and the transaction cannot.
  • The series U (11.32) needs no change. Its fixtures use ClickHouse.

11.34 The MongoDB source in the access layer

A mongodb block is a node source:<id> of the tree of 11.15, as a clickhouse block and a postgres block are. The access layer does not tell the kinds apart. The rules of 11.33 apply, with these changes:

  • The questions of 11.21 are the same. source.query on S(s) covers a save, a draft run and a preview on a MongoDB source. dashboard.read covers a panel query and an options query.
  • The PDP never gets the kind of a source, the database, the collection or the query. A rule of the PDP names the source id only. The page gets the kind from GET /api/sources (6.22).
  • The action document (11.18) holds one resource for each source block of the three kinds. Its description of the type source does not name a kind.
  • The ceilings max_rows and max_duration apply as 11.24 says. Hune enforces them in its own client, with the checks of 8b.6 and 8b.7. A ceiling of 0 gives 403 ceiling_exceeded before Hune sends the query.
  • A grant of source.query gives each read that the user of the source permits (8b.13), on the databases and the collections of the block. It gives no write: the user cannot write, and the connection sends only read commands.
  • The query text, the collection and the database are not facts of a question. A rule of the PDP cannot permit one collection and refuse another. The operator uses one source block for each set of collections that needs another rule.
  • The series U (11.32) needs no change. Its fixtures use ClickHouse.

11.35 A write into a read-only store

A configuration can have a primary store. Each other store is read-only (5.42). Hune never writes into a read-only store, whatever the PDP says.

  1. The rule applies to a create, a save, a delete, a restore, a move and a change of a folder. It applies to a draft of a dashboard or of a folder (the preview and validate_only).
  2. A move needs the primary store for the dashboard and for the target folder.
  3. Hune finds the store of the target in the catalog, with no read of the store.
  4. In the mode open, Hune answers 403 read_only_store at once.
  5. In the mode authzen, Hune asks one question first: dashboard.read on N(uid), or on F(folder) for a folder. The question uses no kept answer (11.27).
  6. When the PDP answers false, the answer is the 403 forbidden of any other write of the route, with the member action equal to dashboard.write (11.30). The body does not show that the target is in a read-only store. The same holds for a uid or a folder that does not exist (11.23).
  7. When the PDP answers true, the answer is 403 read_only_store. Hune never asks dashboard.write for the target. A grant of dashboard.write on the service, on a folder or on a dashboard of a read-only store changes nothing.
  8. The flag access.write of a folder and of a dashboard of a read-only store is false, with no question (11.25). The right to see the SQL needs dashboard.write. So nobody has it on a dashboard of a read-only store in the mode authzen.
  9. The action document is the same as for any configuration with a primary store (11.18). It names the actions by type of resource, not by store. For a resource of a read-only store, the actions that matter are dashboard.read and source.query of the query routes. Hune never uses dashboard.write for such a resource.

The case K321 holds for a target of a read-only store. A subject with no right on it gets the same answer for a target that exists and for one that does not.

12.5 The open mode warning

At each start in the mode open, Hune writes one config.warning line with key = "access.mode" and this message: "access.mode is open: Hune checks no identity and asks no PDP. A proxy that authenticates the users must guard each route of server.listen."

In the mode open, each request that reaches server.listen can read each dashboard and run its queries. With a primary store, it can also change each dashboard of this store. A change of the SQL runs that SQL with the ClickHouse account of Hune. The mode open is thus safe only behind a proxy that authenticates each request.

The mode open fits a deployment where the proxy guards the whole prefix with auth_request. A proxy can guard the prefix /grafana/ of a Grafana instance in the same way.

12.6 Deployment rules

These rules apply to each deployment. The examples of section 17 follow them.

  1. In the mode open, a proxy that authenticates the users MUST guard each route of server.listen.
  2. In the mode authzen, Hune MUST receive requests only through the edge (P 9.4). Use a firewall, a network policy or a private network.
  3. Do not publish server.listen or server.ops_listen to an untrusted network.
  4. The proxy MUST NOT route a public path to server.ops_listen. Only the container platform and the monitoring reach it.
  5. The proxy terminates TLS. The link from the proxy to Hune is on a private network or on the loopback interface.
  6. The proxy passes the header Host unchanged, or sets X-Forwarded-Host. The write guard needs it (12.7).
  7. The proxy adds Strict-Transport-Security. It does not replace the headers of 12.8.
  8. The proxy does not cache the answers of /api/.
  9. The keep-alive timeout of the proxy to Hune is less than server.idle_timeout.
  10. In the mode authzen, the edge replaces the token header that a client sends (P 9.1).

An example with server.base_path = "/dashboards/". Copy the auth_request lines of the location that guards your Grafana instance:

nginx
location /dashboards/ {

    proxy_pass         http://hune:8080;
    proxy_http_version 1.1;
    proxy_set_header   Connection "";
    proxy_set_header   Host $host;
    proxy_set_header   X-Request-Id $request_id;
}

The port of server.ops_listen is not in a location of nginx. The compose file publishes it at most on the loopback address of the host (127.0.0.1).

12.7 The write guard

A page of another site must not use the browser of a person to change a dashboard or to run a query. A proxy with auth_request and a ProcurAuth edge both authenticate the browser with a cookie. A hostile page can make the browser send that cookie. Thus the guard applies in both modes.

Each POST, PUT and DELETE on server.listen passes the guard before Hune reads the body. This includes the panel query, the variable options and the preview.

  • When the request has Sec-Fetch-Site, its value must be same-origin or none. Else the answer is 403 cross_site_request.
  • When the request has no Sec-Fetch-Site but has Origin, the host and port of Origin must equal the header Host. When the request has X-Forwarded-Host, its first value replaces Host for this check. Origin: null fails. Else the answer is 403 cross_site_request.
  • A host without a port has the default port of the scheme of Origin: 80 for http and 443 for https. Thus Origin: https://hune.example equals Host: hune.example:443.
  • A request with a body must have Content-Type: application/json, with an optional parameter charset=utf-8. Else the answer is 415 unsupported_media_type. A page of another site cannot send this type without a CORS preflight.
  • No answer has an Access-Control-Allow-* header. OPTIONS gets 405 with no CORS header, so no preflight ever succeeds.
  • Hune sets no cookie.

A client that is not a browser sends neither Sec-Fetch-Site nor Origin. It passes the guard, for example curl or a test. The token check (11.8) and the proxy still apply to it.

12.8a Compression and BREACH

With server.compress_static = true (the default, 13.8), Hune sends a gzip copy of a static file of a text type (9.3). It compresses no other answer. This section gives the security reasons.

BREACH and the attacks of its type (TIME, HEIST) read a secret from the size of compressed answers. Such an attack needs all of these conditions:

  1. The compressed body holds a secret, for example a token or a value of one user.
  2. The same body holds a text that the attacker controls, such as a part of the URL.
  3. The attacker sees the size of many answers to requests that the attacker chooses.

Hune makes sure that conditions 1 and 2 are never true for a compressed answer:

  • A static file holds no secret and no value of a user. Its bytes are fixed at build time, and each user gets the same bytes.
  • No part of a request goes into a static file. This includes the path, the query, each header and the identity token.
  • The server makes each copy one time at start. The choice of the copy depends only on the file, on Accept-Encoding and on the key. The size of an answer thus tells only the size of a public file.
  • The shell, each answer under /api/, each error and each answer of the ops listener are never compressed. The shell holds no secret, but it is not a static file (6.25).
  • In the mode authzen, a static file needs a valid identity token (6.25). The token is in a request header and never in a body.

Two other points apply:

  • CRIME used the compression of TLS. rustls has no TLS compression, so CRIME does not apply.
  • A request never starts a compression. Thus a client cannot use the compression to load the CPU. The time of an answer does not show its content.

A later change can compress another answer only after a written proof. The proof MUST show that the answer holds no secret, or no text from a request. Without this proof, the answer MUST NOT be compressed.

12.8b The tile source of the map: privacy

The map of 9.19i can draw tiles of a host outside Hune. These rules apply:

  • The feature is off by default. Without the block geomap (13.12c), no page contacts a host other than Hune, and the policy of 12.8 does not change.
  • With the block, the browser of each viewer contacts the tile host for each tile of a view. The host gets the address of the viewer, the User-Agent, the Accept-Language, the time and the rate of the requests. It also gets the header Origin with the origin of Hune, and the tile coordinates z, x and y. The coordinates tell the area that the viewer looks at, and this is often the area of the data.
  • Hune sends no cookie, no Referer, no identity token, no uid, no title, no variable and no value of the data to the tile host.
  • An IP address is personal data. Read the terms of the provider. Make an agreement for the data with the provider where the law needs one.
  • The public servers of OpenStreetMap forbid heavy use, and they can refuse a request with no Referer. Use a provider with a contract, or your own tile server.
  • Your own tile server, or a tile cache on the same edge as Hune, removes the third party. Each request then stays inside your network.
  • A compromised tile host can show wrong images or track the viewers. It cannot run a script, because the page loads only images from it, and the policy gives it no script source.
  • The browser downloads all the bytes of a tile before the page can check its size. The page cannot cap these bytes, because it loads each tile as an image and connect-src stays 'self'. Thus a hostile or compromised tile host can use the bandwidth of each viewer. The page keeps only the decoded tiles, 256 at most (64 MiB). It does not ask again for a failed tile in the same view (9.19i).
  • An edge that sets its own policy must also permit the tile host in img-src.
  • To turn the feature off, remove the block and restart Hune (13.26).

12.9 SQL safety

Section 7 gives the complete rules. In short:

  • The server is the only place that builds SQL. A viewer sends no SQL.
  • The server expands the macros and the variables. It escapes each value by its place in the SQL, and the ClickHouse lexer finds that place. A free text value can only become a literal. An identifier or a raw fragment comes only from a closed list.
  • One statement, whose first keyword is SELECT or WITH. Hune refuses any other statement at save and at run.
  • The SQL goes in the body of a POST to ClickHouse, never in a URL. The values of the query parameters of ClickHouse (7.6a) go in the URL as param_<name>, and never in the SQL text.
  • These checks are not the security boundary. The ClickHouse account is the boundary (12.12).
  • The ad hoc filters of an adhoc variable (4.10c, 7.7a, 7.10a) are values only. The key is only compared with the configured list, the operator is = or !=, and each value is a string literal. The exposure note below applies.
  • The macro $__adhocFilters is one term of the top-level AND of the WHERE or PREWHERE clause of the outer statement (7.10a, rule 4). So a filter never adds a row that the rest of the clause refuses. The rule is about the clause and not about the result. A LIMIT, an aggregate or a window function can still show other rows, because the filter removes rows first.
  • The syntax tree of the SQL area is never a security check. It never changes what the server accepts or refuses, and a fault of the tree never stops a save or a run (10.3c, rule 1).

The exposure of a listed column. Each column of clickhouse "<id>".adhoc_columns is exposed to each viewer of each dashboard on that source whose SQL has $__adhocFilters. With = and !=, a viewer can test a guess of a value and read the count or the sum that the panel shows. A viewer can thus learn which values a listed column holds in the rows of the panel. List only the columns that each viewer of the dashboards of the source may read. The list is empty by default: with the key absent, no filter applies on the source.

For a postgres source, the same rules hold with the dialect of 7.19 to 7.26. The SQL goes in one Parse message, never in a URL and never by the simple protocol. The first word is SELECT, WITH, VALUES or TABLE. The role of 8a.13 and the read-only transaction are the boundary (12.19).

For a mongodb source, the query is a JSON tree and not SQL. The parser reads it with the profile of 7.28.

  • The grammar is a closed allowlist of stages and operators (7.31).
  • Each value of a variable is a typed leaf of the tree (7.34, 7.35).
  • The command goes to the server as BSON. It is never a text, and it never goes in a URL.
  • The user of 8b.13 and the closed list of commands of 8b.5 are the boundary (12.20).

12.10 Secrets

The secrets are the passwords of the ClickHouse, postgres and mongodb sources, the PostgreSQL password of the store, and the PDP token.

  • A secret accepts only _env and _file (13.5). A secret in clear text in the file stops the start.
  • Hune reads each secret one time, at start. A change of a secret needs a restart (14.21).
  • A secret never shows in a log line, an error, print-config, a metric, a span or an answer. print-config and the start log show <hidden>.
  • The type that holds a secret has no Debug or Display form that shows the value.
  • The ClickHouse credentials go in the headers X-ClickHouse-User and X-ClickHouse-Key, never in a URL (section 8).
  • The password of a postgres source goes in the SCRAM-SHA-256 exchange of tokio-postgres. With sslmode = "verify-full", Hune also requires channel binding (8a.4).
  • The password of a mongodb source goes in the SCRAM-SHA-256 exchange of the driver. Hune offers no other mechanism, so a server cannot make it send the password in clear text (8b.4). Hune sets the options of the driver in code, never in a connection string.
  • The PDP token goes in Authorization: Bearer on the link to the PDP (11.12).
  • The PostgreSQL password goes in the SCRAM-SHA-256 exchange of tokio-postgres. With sslmode = "verify-full", Hune also requires channel binding (12.13).
  • A secret file is readable by the user 65532 (the user of the image) and by no other user of the host. Hune does not check the mode of the file. Hune writes no secret to a file.
  • The identity token is not a secret of Hune, but Hune never logs it (12.15).

12.11 Path safety

  • The volume: section 5 gives the rules. The root is absolute and canonical, and Hune opens it one time as a directory. Each later access uses openat with O_NOFOLLOW. Each name comes from a validated id. Hune follows and makes no symbolic link, in both modes.
  • Each path of the configuration (_file values, ca_file, path of a volume) MUST be absolute. A relative path stops the start (13.6).
  • A _file value and a CA file must be regular files. Hune does not follow a symbolic link in their last part.
  • Hune never builds a path from a value of a request, except from an id that passed the id rule of section 4.

12.12 The ClickHouse account

The ClickHouse account is the real boundary of the SQL. 8.12 gives the contract of this account, and it is the only contract. This paragraph is a summary, and 8.12 wins over it. The contract has these items:

  • A dedicated user, not default.
  • A settings profile with readonly = 2: the user can send settings, and ClickHouse refuses each write.
  • MAX constraints on max_execution_time, max_result_rows, max_result_bytes, max_rows_to_read, max_memory_usage and max_query_size. Each MAX is at least the value of the key of each block of the account.
  • CONST constraints with the value throw on result_overflow_mode, timeout_overflow_mode and read_overflow_mode. Thus authored SQL cannot cut a result and show it as complete.
  • SELECT grants only, on the databases that the dashboards read.
  • No grant of the kind SOURCES (URL, S3, REMOTE, FILE, MONGO and the others). Thus authored SQL cannot reach the network or the disk of the ClickHouse host.
  • No KILL QUERY grant, no access management grant, and no other grant. Cancellation uses the close of the connection (section 8).

12.13 The PostgreSQL account

  • hune serve uses a role with CONNECT on the database and only SELECT, INSERT, UPDATE and DELETE on the tables of Hune. This role cannot change the schema.
  • hune migrate-store uses the owner role through its own configuration file migrate.hcl (section 5).
  • Neither role is a superuser.
  • hune serve MUST stop at start when its role is a superuser. It MUST also stop when its role owns a table of Hune (5.25, step 6 of 5.29). A member of the role that owns a table counts as an owner. Hune then writes server.start_failed and exits with 1 (14.12).
  • The message names the rule. It is the text of 5.29: storage.postgres: the role <user> is a superuser or owns the Hune tables; serve needs a role with only SELECT, INSERT, UPDATE and DELETE (5.25, 12.13).
  • The server authenticates the roles with scram-sha-256 in pg_hba.conf.
  • With sslmode = "verify-full", Hune sets channel_binding = require in tokio-postgres. The server must then authenticate with SCRAM-SHA-256 with channel binding, and the methods password and md5 fail.
  • With sslmode = "disable", Hune cannot refuse a weak method. pg_hba.conf is then the only control.
  • storage.postgres.sslmode = "verify-full" is the rule. sslmode = "disable" is only for a private network or the loopback interface. Hune writes a config.warning for it when the host is not a loopback address (13.15).

12.15 Sensitive data in logs, metrics and traces

Hune never writes these values to a log line, a metric label or a span attribute:

  • Row data of a result.
  • SQL text, stored or expanded. A log line can hold the SHA-256 of the expanded SQL (hexadecimal). Read the note on this hash below.
  • Variable values.
  • A secret, the identity token, Authorization, Cookie and the value of the token header.
  • The query string of a URL. The log holds the route template (for example /api/dashboards/{uid}) and the ids of the path.
  • A request body or an answer body.
  • The text of a ClickHouse exception. A log line holds the ClickHouse error code only.
  • The text of a PostgreSQL error. A log line holds the SQLSTATE only.
  • The text of a MongoDB error. A log line holds the server code only.
  • The query tree of a MongoDB source, stored or expanded. A log line can hold the SHA-256 of the compact text of the expanded command (8b.11).
  • The values of the query parameters of 7.6a. They go to ClickHouse in the request URI (8.3), and Hune never logs this URI.

These values are permitted in a log line:

  • the subject (sub) and the claim owner (P 9.5);
  • the client address and the request id;
  • the uid, the folder id, the panel id, the source id and the query_id;
  • the reason of a PDP answer (P 10.3 forbids it only in the answer to the client);
  • the error codes. A metric label holds no id of a dashboard, a folder or a subject

(14.8).

The values of the query parameters of 7.6a travel in the request URI to ClickHouse, as param_<name> (8.3). ClickHouse writes this URI to its own log at the level debug or trace. A proxy in front of ClickHouse can write it to its access log. The operator keeps the ClickHouse log at the level information or higher, or treats that log as data of the same class as system.query_log.

The table system.query_log already holds the final SQL, with the values of the text form of 7.6. ClickHouse 26.8 also writes the statement there with the value of each query parameter in place of its form (case C41). Thus query parameters add no new class of data to that table.

The hash sql_sha256 of the event query.run (14.7) is a fingerprint of the values. The expanded SQL holds each value of the text form of 7.6 and each value of an ad hoc filter (7.10a). A person with the log and the stored SQL can compute the hash for a guessed value. When the value has few possible texts, this person can thus find the value offline. The values of the query parameters of 7.6a are not in the expanded SQL, so the hash does not show them. Give the log of Hune the access control and the retention of system.query_log.

Hune does not use a keyed hash. The hash must equal the SHA-256 of the member sql of Inspect (6.20), and the tests compare the two.

The two body constants bound the memory of the bodies in flight: 8 times server.max_request_bytes, plus 256 times 512 KiB.

The limits of the work before and after a decision:

  • The work before the decision is linear in the bytes of the body. It is the body read, the check of the JSON syntax and the pre-pass of the sources (11.20, 11.21). Hune never validates a document before the decision.
  • A validation runs in spawn_blocking and never on an async worker (3.7). It takes a permit of MAX_INFLIGHT_VALIDATIONS first. Thus the validations cannot take the threads of the PDP calls or of the store.
  • A validation keeps its permit and the place of its body until it ends, also when the client closes the connection. The validation of a create or of a save also keeps its place while it waits for its permit. Thus the 8 places bound the work of the requests that the clients left, and a ninth document body gets 503 server_busy.
  • A restore and the plain read of a version (6.17) take the permit before the store read. Thus a request that waits holds no bytes of a version.
  • A restore validates its version one time, before the store (6.18). Under its lock, the store reads only the metadata of the version and the current document. Thus a restore holds the store lock for no validation of a version.
  • A subject can hold the 8 places with slow bodies before any decision. The caps of a subject stop this. In the mode open, all requests have the subject -, so these caps apply in the mode authzen only.
  • The list of errors of a validation holds at most MAX_ERRORS items, and its list of warnings at most MAX_WARNINGS items (4.35, 4.36, 6.13).

The codes server_busy, request_timeout, uri_too_long, headers_too_large, payload_too_large, source_busy and storage_unavailable are in the list of section 6 (6.8).

12.17 Supply chain

  • Cargo.lock is in the repository. Each build runs with --locked.
  • Each direct dependency has an exact version (=x.y.z), default-features = false, and a comment of one line that gives its reason.
  • rust-toolchain.toml pins the toolchain. The builder image is pinned by its digest.
  • cargo deny check runs in the CI job policy. It checks the advisories, the licences (a list of permitted licences), the bans and the sources.
  • The bans include openssl, native-tls, rustls-native-certs, webpki-roots, reqwest and aws-lc-rs.
  • The permitted sources are crates.io and the one git URL of 11.10. The policy unknown-git and unknown-registry is deny.
  • deps.lock.txt is in the repository: the sorted list of name version of the resolved graph for the two musl targets. The job policy compares it with the output of cargo metadata --locked. Thus each new crate is a reviewed diff.
  • unsafe_code = "forbid" applies to each crate of the workspace.
  • The code has no std::process::Command. The job policy checks it with a search of the sources.
  • The job policy searches the sources for the pattern std::env::(var|var_os|vars|vars_os|set_var|remove_var)\b. It permits a match only in crates/hclconf/src/env.rs, in the tests and in each build.rs.
  • The copy of the chart engine of ClickHouse Dash has a lock file with the SHA-256 of each file (section 9). The job policy checks the copy against its lock file. The crate hclconf has a PROVENANCE file. It records that the crate is not a copy.
  • The product has no npm package. npm runs only inside the image of the browser tests.
  • The release has SHA256SUMS, and the same sources give the same bytes (section 17). Hune never pushes an image to a registry.

12.18 What Hune does not protect

  • In the mode open, each request that reaches server.listen is trusted. The proxy is the only access control.
  • A grant of dashboard.read gives each row that the stored SQL of the dashboard reads. Hune does not filter rows by subject.
  • A grant of source.query gives each read that the ClickHouse account permits.
  • A grant of source.query gives each read that the role of a PostgreSQL source permits (8a.13). The role limits the data. The closed grammar does not.
  • A grant of source.query gives each read that the user of a MongoDB source permits (8b.13), on the databases of its block. The user limits the data. The closed grammar does not.
  • The client of a MongoDB source has the limits of 8b.15. They are one large reply, a command that runs until maxTimeMS after the client leaves, and the setting security.javascriptEnabled that Hune cannot read.
  • The client of a PostgreSQL source has the limits of 8a.15. They are one large row, the statement_timeout of each message, and the trust in the functions that an administrator wrote.
  • A save does not apply the ceilings of source.query. The saved SQL runs with the ceilings of dashboard.read of the viewer, who can be the author (11.24). Operators SHOULD give each author the same ceilings on both grants.
  • The action document is public. It shows the service id and the label of each source.
  • A revoked grant stays active for access.pdp.cache_ttl at most on each instance.
  • A person with write access to the volume or to the database can change any dashboard and its history. The history is not tamper-evident. On the volume, a change outside Hune shows as an external change (section 5).
  • Several writers on one shared volume (NFS, FUSE) are not supported. flock on these file systems is best effort.
  • A compromised edge can sign any identity. A compromised PDP can grant anything.
  • The draft of the editor stays in localStorage of the browser until the save succeeds (section 10). Another program on that computer can read it. In the mode authzen, a shared browser keeps the draft of a person until a page of another subject removes it (10.8). Until then, the tools of the browser can show it.
  • In the mode open, each history version and each dashboard.changed line has the subject - (14.11). The durable audit then holds no author.
  • A person who can read a dashboard can copy its data, for example with a screenshot or a download.
  • Hune does not encrypt the volume or the database at rest. The operator does it when it is necessary.
  • The link from the proxy to Hune has no TLS. It must stay on a private network (12.6).
  • A valid user can load ClickHouse up to the limits of 12.16. The limits bound the cost. They do not remove it.
  • Differences of time can show that an operation reached the PDP or the store. Hune makes the body, the headers and its own work the same for an item that exists and one that does not exist (11.23, T98). On a write route, both items also send the same number of PDP requests. Neither uses a kept answer, so this residual is closed. Two differences stay:
    • The PDP can take another time to evaluate the question of 11.23 than the use of the route.
    • On a read route, a second request for a uid that exists can get a kept answer in one cache_ttl. The question of 11.23 never gets one (11.27).
  • A person who can write a dashboard can write a link whose text names another place than its destination. The page shows the link as the author wrote it, with an underline. The rules of 9.19b make sure that the destination is http, https or relative. They do not check that the text tells the truth. The title of a panel and the text of a note are as reliable as their author.
  • The member allow_custom_value of a query variable is a rule of the page and not a control of security. A closed query variable shows the options, but a person who sends a request can send any value. The server treats it as free text under the properties P, PG and PM. An author who needs a bound writes it in the SQL of the panel (4.8). An open or a closed custom variable has the refusal or the free-text rule of 7.7.
  • A pattern of the document is text that an author wrote: filter_fields_by_name, rename_by_regex, an override, the option reduce, a mapping, filter_by_value and the regex of a variable. The page runs it on names and cells that hold data. A long-to-wide name holds a label value, and a MongoDB column name has no limit. filter_by_value and a mapping read cells.
  • The page runs a pattern only on a text of 1,024 code units or fewer, and a longer text never matches (9.14). This bounds a common pattern such as (.*)-(.*). It does not bound a pattern with nested repetitions such as (a+)+$, which can be slow on a short text. The check of the document does not refuse such a pattern, and the same people can write the pattern and the SQL.
  • The value of a constant and the items of an interval variable are text that an author wrote. The server puts them in the SQL as author text. A person who can write the document can also write the SQL, so the variables give no more power. The account of the source and its readonly profile are the boundary (7.12).
  • The images of the tile host of 13.12c are outside the control of Hune. Hune checks their size and their CORS header (9.19i). It cannot check what they show. The privacy note of 12.8b tells what the host learns.

12.19 The PostgreSQL source account

The role of a postgres source is the real boundary of its SQL. 8a.13 gives the contract of this role, and it is the only contract. This paragraph is a summary, and 8a.13 wins over it. The contract has these items:

  • A dedicated login role, which is not a superuser and not the role of the store.
  • None of the attributes SUPERUSER, CREATEROLE, CREATEDB, REPLICATION and BYPASSRLS. No membership in a predefined role, or in a role with one of these attributes.
  • SELECT grants only, on the schemas that the dashboards read. No CREATE on the database or on a schema. No write privilege on a table, a sequence or a column.
  • No EXECUTE on the functions of dblink and on the functions that read or write files of the server. No USAGE on a foreign data wrapper or a foreign server.
  • The settings and the revokes of 8a.13, as advice. They give the defaults of the role and temp_file_limit. They remove the DO block and the EXECUTE right of PUBLIC on the functions that the grammar refuses.

The probe of 8a.12 checks the mandatory items and gives the state misconfigured when one fails. The test of 16.9a creates the role with the SQL of 8a.13 and logs in as this role. It checks each write attempt of 8a.13 with a plain client.

12.20 The MongoDB source account

The user of a mongodb source is the real boundary of its queries. 8b.13 gives the contract of this user, and it is the only contract. This paragraph is a summary, and 8b.13 wins over it. The contract has these items:

  • A dedicated login, which is not an administrator. The mechanism is SCRAM-SHA-256.
  • The built-in role read on each database of the key databases, and no other role (M2).
  • No privilege on cluster or anyResource, and no action that the read role does not hold (M3).
  • The server settings of 8b.13, as advice: security.authorization, security.javascriptEnabled: false and TLS only. Hune cannot check the second one, because the user cannot read it.

The probe of 8b.12 checks the mandatory items with connectionStatus and showPrivileges, and gives the state misconfigured when one fails. The test of 16.9b creates the user with the commands of 8b.13 and logs in as this user. It checks each write attempt of 8b.13 with a plain client.
